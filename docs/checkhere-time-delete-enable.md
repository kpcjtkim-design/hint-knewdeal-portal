# 체크히어 시간 삭제 켜는 순서 (2026-10-14, 2026-10-16·2026-10-19 고침)

/beta2 출결대조에서 체크히어 퇴실·1교시 시간(기록 번호가 있는 칸)을 지우는 기능을 실제로 켜는 순서다. 코드는 들어가 있지만 아래 **관문 G1·G3이 열려야** 삭제 요청을 만든다(`beta2-checkhere-core.mjs` `deletionGate`). 하나라도 닫혀 있으면 /beta2의 ×는 꺼져 있고 결석 저장은 '보류'로 남는다. 요청은 만들기만 하고(승인 대기), 체크히어에서 지우는 것은 관리자가 운영포털 「반영 요청·승인」에서 승인할 때다(0-1절의 승인 때 확인).

| 관문 | 무엇 | 누가 |
|---|---|---|
| G1 | `settings/checkhereFeatures.timeDeleteRules` = `true` | 사용자(Firebase 콘솔) |
| ~~G2~~ | **2026-10-16부터 요청 만들기에 필요 없음**(사용자 결정 "/beta2 삭제 요청은 중계 없이도 만들 수 있게"). 중계 신호 `settings/checkhereRelay`는 능력(v1·v2) 판단과 자동 수집·해제 상태 표시에만 쓴다(0-1절) | — |
| G3 | 그 화면에서 Firestore 권한 거절(permission-denied)을 보지 않음 | 규칙 게시(사용자) |

삭제 안전 규칙(사용자 결정 2026-10-14): 기록 번호(eventId)가 있는 칸만 지운다. 퇴실(COMPLETE)과 관리자가 넣은 1교시(ATTEND)가 해당하고, 체크인으로 계산된 1교시(PASS)와 실제 입실(ENTER)은 절대 지우지 않는다(`checkhere/rules.mjs` `timeDeleteRefusal`). 승인 뒤 체크히어 시간이 바뀌었으면 지우지 않고 '원본 변경'으로 끝난다.

## 0. 2026-10-16에 바뀐 것 (build `20261016.2`)

실제 체크히어에서 확인한 동작(`docs/cowork/2026-10-16-checkhere-write-format.md` 2-1~2-3)과 사용자 결정("입실기록 자체는 남아도 됨. 09~18(1교시)이랑 퇴실시간만 깔끔히 지워지면 됨")에 맞췄다.

- **관리자 1교시(ATTEND) 삭제를 켰다**(`rules.mjs` `ATTEND_DELETE=true`). 단, 두 칸 삭제를 아는 연결 프로그램(`time-delete-v2`)일 때만. 옛 연결 프로그램(v1뿐)이면 예전처럼 퇴실만 지운다.
- **두 칸 삭제 순서(`rules.mjs` `DELETE_ORDER=['exit','entry']`)**: 퇴실이 남은 채 1교시만 지우면 체크히어가 퇴실 시간으로 입실·1교시를 다시 채워 18:00/18:00/18:00/0분이 된다(깨끗하지 않음). 그래서 연결 프로그램은 ① 퇴실 삭제 → ② 다시 읽기 → ③ 1교시가 아직 번호 있는 ATTEND면 **다시 읽은 번호로** 삭제 → ④ 다시 읽어 퇴실·1교시가 모두 비었는지 확인한다. 깨끗하면 '완료'(결과 글 '퇴실·1교시 삭제 확인', 입실이 남으면 '입실 기록은 남음'), 아니면 '일부 반영'(결과 글 '덜 지워짐: …', 남은 종류·시간만).
- 입실은 남을 수 있다(1교시 메모를 가진 ENTER가 남아 입실 09:00이 보일 수 있음). 사용자 결정으로 괜찮다.
- **퇴실이 남은 1교시만 삭제는 거절**한다(`rules.mjs`: '퇴실이 남아 있으면 1교시만 지울 수 없습니다(…). 퇴실과 함께 지워 주세요.'). 1기 운영포털 승인도, 연결 프로그램도 같은 규칙으로 막는다.
- 체크인한 학생이 1교시에 사유를 저장해 ATTEND가 된 기록도 퇴실과 함께 지운다(두 칸만 깨끗이). 실제 입실(ENTER)은 그대로다.
- **마스킹 관문**: 수정·삭제는 사람이 수집 PC 체크히어 탭의 마스킹을 해제했고 남은 시간이 150초 이상일 때만 한다(`rules.mjs` `privacyState`·`PRIVACY_MIN_WRITE_SECONDS`). 읽기·수집·요청 만들기는 가려도 된다. 프로그램은 해제·연장·종료를 누르지 않는다(5절).

| | `time-delete-v2` 있음(또는 중계 신호 없음, 0-1절) | v1만(마지막 신호가 옛 연결 프로그램) |
|---|---|---|
| 결석 저장 · 관리자 1교시 학생 | 1교시·퇴실 두 칸 삭제 요청(`deleteTimes ['entry','exit']`) | 보류('1교시 삭제는 수집 PC 프로그램 업데이트 후 가능 (time-delete-v2) · 퇴실도 그대로 둡니다…') |
| 결석 저장 · 체크인 학생(PASS) | 퇴실만(`['exit']`, 계산된 1교시도 함께 빔) | 같음 |
| 퇴실 × · 관리자 1교시 학생 | **1교시·퇴실 두 칸**(`['entry','exit']`, 2026-10-19) | 퇴실만 지움(관리자 1교시와 입실은 남음) |
| 퇴실 × · 체크인 학생(PASS) | 퇴실만(`['exit']`, 계산된 1교시도 함께 빔 — 연결 프로그램이 1교시도 빈 것을 확인) | 같음 |
| 1교시 × · 퇴실 있음 | **1교시·퇴실 두 칸**(`['entry','exit']`, 2026-10-19, 예전에는 꺼짐) | 꺼짐(title: 1교시 삭제는 수집 PC 프로그램 업데이트 후 가능) |
| 1교시 × · 퇴실 없음 | 1교시만(`['entry']`) | 꺼짐(같은 title) |

### × 한 번에 두 칸 (2026-10-19, 사용자 결정 "둘 다 삭제돼야 함")

실제 체크히어 시험에서 관리자 1교시(ATTEND) 학생의 퇴실 ×를 눌렀더니 퇴실만 지워지고 09:00~18:00 칸(1교시)은 그대로 남았다. 사용자 결정: 삭제 한 번에 두 칸이 모두 지워져야 한다.

- v2(`time-delete-v2`, 또는 중계 신호 없음 — 0-1절)면 관리자 1교시(ATTEND, 1교시 기록 번호 있음)와 퇴실이 모두 있는 학생은 **퇴실 ×든 1교시 ×든** 1교시·퇴실 두 칸 요청 1건을 만든다(`beta2-checkhere-core.mjs` `removalSides`, `beta2-checkhere-sync.mjs` `timeDeletePlan`). 연결 프로그램은 결석 두 칸과 똑같이 퇴실 먼저 지우고, 다시 읽은 1교시를 지운 뒤 두 칸이 빈 것을 확인한다(0절).
- 체크인 학생(PASS)의 퇴실 ×는 그대로 퇴실만(`['exit']`): 체크히어가 계산된 1교시를 함께 비우고, 연결 프로그램이 끝에 1교시도 빈 것을 확인한다(`writeback.mjs` `passWithExit`). PASS 1교시 ×는 계속 꺼짐.
- 두 칸이면 두 칸 모두 출결원장 유형을 본다: 지각류·외출류·인정출석(1교시를 씀)이면 퇴실 ×도, 조퇴류(퇴실을 씀)면 1교시 ×도 '유형을 먼저 바꿔 주세요 (결석으로 바꾸면 지울 수 있는 시간을 함께 지웁니다)'로 꺼진다.
- 함께 지울 퇴실의 기록 번호가 없으면 1교시 ×도 그 이유('퇴실 기록 번호를 확인하지 못했습니다(다시 수집 필요).')로 꺼진다. 1교시 기록 번호가 없는 관리자 기록(다시 수집 필요)이면 퇴실 ×는 퇴실만이고, 확인창이 '관리자가 넣은 1교시와 체크히어 입실 기록은 남습니다'라고 알린다(결석 보류 글의 '퇴실만 지우려면 ×'와 같음).
- 옛 연결 프로그램(v1)이면 예전 그대로: 퇴실 ×는 퇴실만, 1교시 ×는 꺼짐(업데이트 안내).
- 확인창이 말한 칸과 보내는 칸은 같다: 3초 동안 중계 신호의 능력이 바뀌어(v1 → v2: 연결 프로그램 업데이트, v2 → v1) 지울 칸이 달라지면(퇴실만 ↔ 두 칸) 받은 확인을 버리고 새 칸으로 다시 묻는다(아니오면 쓰지 않음). 지금 보내기(반·날짜 이동·떠남)면 묻지 않고 '시간 삭제는 확인 없이 보내지 않습니다'로 멈춘다(`beta2-checkhere-sync.mjs` `commit`의 `okTimes`).
- 결석 저장은 바뀌지 않았다(v2 두 칸, PASS 퇴실만, v1 보류).

확인창의 '남는 것': 두 칸이면 '퇴실과 1교시(09:00~18:00 칸)를 함께 지웁니다. 입실 기록은 남을 수 있습니다.'(1교시 칸 이름은 그 강의시간, 2026-10-19 문구), 퇴실이 빈 1교시만이면 '1교시·퇴실 칸은 비워지고 체크히어 입실 기록은 남을 수 있습니다', 관리자 1교시 학생의 퇴실만이면(v1) '관리자가 넣은 1교시와 체크히어 입실 기록은 남습니다', 체크인 학생의 퇴실만이면 '체크히어 실제 입실 기록은 남습니다'(+ '퇴실을 지우면 1교시(HH:MM)와 총 참여 시간도 비워집니다.'). 가렸거나 해제 상태를 모르면 '반영할 때 체크히어 마스킹 해제 필요.'를 덧붙이는 규칙은 그대로다.

## 0-1. 중계 없이 삭제 요청 만들기 (2026-10-16)

중계(수집 PC의 `checkhere-live.html` 탭)는 읽기 전용이다. 꺼져 있어도 /beta2는 삭제 요청을 만든다. 중계가 하는 일은 두 가지뿐이다: 체크히어 기록 자동 수집(10분)과 체크히어 해제 상태 표시.

- **능력(v1·v2)**: 마지막 중계 신호의 `capabilities`를 그대로 쓴다(시각·`state` 무관, 오래되거나 멈춘 신호도 됨 — 연결 프로그램은 올라가기만 하고 내려가지 않는다).

  | 마지막 신호 | /beta2 동작 |
  |---|---|
  | `time-delete-v2` 있음 | v2: 두 칸 삭제(관리자 1교시 학생 결석·퇴실 ×·1교시 × → `['entry','exit']`, 체크인 학생 → `['exit']`, 퇴실이 빈 1교시 × → `['entry']`, 0절 '× 한 번에 두 칸') |
  | `time-delete-v1`만 | v1: 예전처럼 퇴실만(관리자 1교시 학생 결석은 보류, 1교시 × 꺼짐) |
  | 신호 문서 없음, 또는 능력 목록 없음·빈 목록(중계가 연결 프로그램에 한 번도 닿지 못함, 또는 옛 중계 탭이 연결 프로그램에 닿지 못할 때 쓴 빈 목록) | v2로 본다(지금 연결 프로그램 build `20261016.2`) |
  | 닿은 신호인데 둘 다 없음(옛 연결 프로그램) | × 꺼짐, title '수집 PC 프로그램 업데이트 필요 (time-delete-v2)' |

  중계는 연결 프로그램에 닿지 않을 때(창을 닫음·PC 잠듦)도 마지막으로 본 능력을 그대로 신호에 쓴다(해제 상태 `privacy`만 뺀다, `checkhere-live-relay.mjs` `relaySignal`). 그래서 옛(v1) 연결 프로그램이 잠시 꺼져도 /beta2가 v2(두 칸 요청)로 바뀌지 않는다. 배포 뒤 중계 탭을 새로고침해야 이렇게 쓴다(1절 2).

- **해제 상태 표시**: 중계가 꺼져 있으면(신호가 3분 넘음·멈춤) 해제 상태를 모른다. 도구줄 중계 표시는 '중계 꺼짐 · 자동 수집·해제 표시 없음 (삭제 요청은 가능, 반영은 승인 때)'(삭제 조건이 닫혀 있으면 — G1·G3 또는 업데이트 필요 — '삭제 '가 빠진 '(요청은 가능, 반영은 승인 때)'), title 첫 줄은 '체크히어 해제 상태는 중계가 켜져 있을 때 보입니다.'. 해제 상태를 모르거나(중계 꺼짐·privacy 없는 옛 중계) 쓸 수 없으면 확인창과 × title에 '반영할 때 체크히어 마스킹 해제 필요'를 붙인다.
- **승인 때 확인**(삭제는 여기서만 일어난다. 거절되면 요청은 승인 대기 그대로이고 실패·반려로 바뀌지 않는다):
  - 운영포털 「반영 요청·승인」(`checkhere-requests.mjs` `judgeRequest`): 연결 프로그램에 `time-delete-v1`이 없으면 '…체크히어 시간 삭제 지원이 필요합니다.', 1교시가 든 삭제(1교시만·두 칸)에 `time-delete-v2`가 없으면 '수집 PC에서 최신 체크히어 시작.cmd를 다시 실행해 주세요. 1교시 삭제는 time-delete-v2 지원이 필요합니다. 그 전에는 이 요청을 반영할 수 없습니다. 업데이트 뒤 다시 승인하거나 반려해 주세요.'로 승인 화면을 열지 않는다(두 칸 요청의 퇴실도 지우지 않는다). 신호가 없어 /beta2가 v2로 보고 만든 두 칸 요청이 옛 연결 프로그램을 만나면 여기서 멈춘다(요청 취소·반려 또는 연결 프로그램 업데이트 뒤 승인).
  - 마스킹 관문: 체크히어 탭이 해제됐고 남은 시간이 150초 이상일 때만 보낸다(5절).
  - 연결 프로그램(`server.mjs`): `time-delete-v1`을 모르면 삭제 승인을 거절. `rules.mjs` `timeDeleteRefusal`: 1교시는 퇴실과 함께이거나 퇴실이 이미 빈 때만. `ATTEND_DELETE=false`인 옛 연결 프로그램은 아무것도 누르기 전에 1교시 삭제를 충돌로 거절한다.

## 1. 웹 코드 배포 (사용자 확인 후)

1. 브랜치 커밋 → push → PR 병합 → Vercel 배포. 바뀌는 화면: /beta2 출결대조, 1기 운영포털 체크히어(수집·검수, 반영 요청·승인), `/checkhere-live.html`(중계 탭).
2. 배포 뒤 /beta2와 중계 탭을 **강력 새로고침**(Ctrl+Shift+R). `beta2-admin.mjs`가 `beta2-ledger.mjs`·`beta2-checkhere-sync.mjs`를 버전 없이 불러오므로 옛 코드가 남을 수 있다.
3. 확인: /beta2 출결대조 도구줄에 '중계 꺼짐 · 자동 수집·해제 표시 없음 (…)' 또는 '수집 PC 중계 작동 중' 표시가 보이면 새 코드다(옛 코드는 '중계 꺼짐 · 체크히어 기록 10분 갱신 멈춤'). 새 연결 프로그램과 중계가 돌면 그 뒤에 '체크히어 가림 · 읽기만' 또는 '체크히어 해제됨 · N분 남음'이 붙는다.
4. 웹과 연결 프로그램은 **함께** 바꾼다(2절). 섞인 경우: 새 웹 + 옛 연결 프로그램(v2 없음) → 마지막 중계 신호가 v1이면 퇴실만 지움, 신호가 없으면 /beta2가 두 칸 요청을 만들 수 있지만 승인 화면이 '1교시 삭제는 time-delete-v2 지원이 필요합니다'로 막는다(0-1절). 새 연결 프로그램 + 옛 웹 → 연결 프로그램이 두 칸 순서·퇴실이 남은 1교시 거절·마스킹 관문을 그대로 지킨다.

## 2. 수집 PC 연결 프로그램 바꾸기 (build `20261016.2`)

1. 수집·반영이 없는 시간에 한다(`Start.ps1`은 작업 중이면 재시작을 거절한다).
2. 이 저장소로 옮길 때: 옛 폴더의 `checkhere/data/`를 이 저장소 `checkhere/data/`로 **복사만** 한다(수집 이력·강의 주소·로그인 프로필, 커밋 금지). 복사하지 않으면 전용 크롬에서 체크히어에 다시 로그인한다.
3. 이 저장소의 `checkhere/체크히어 시작.cmd`를 실행한다. 옛 연결 프로그램이 돌고 있으면 끄고 새 것을 띄운다.
4. 연결 키가 바뀐다. 중계 탭에서 '중계 멈춤' → 새 키 붙여넣기 → '중계 시작'. 운영포털 체크히어 탭도 새 키를 넣는다.
5. 중계 신호 확인(선택 — 자동 수집·해제 상태 표시·능력 알림용, 삭제 요청 만들기에는 필요 없음): Firebase 콘솔 데이터 탭에서 `settings/checkhereRelay`를 연다.
   - `state` = `running`, `at`이 1~2분 안, `build` = `20261016.2`, `capabilities`에 `time-delete-v1`·`time-delete-v2`·`privacy-state-v1`.
   - `privacy` = `{state, leftSec, writable}`(체크히어 탭 해제 상태, 연결 프로그램이 셈). 학생 이름·글은 들어 있지 않다.
   - 중계 탭은 작동 중 약 1분마다 이 문서를 고친다.

### 2-1. 체크히어 개인정보 가림(마스킹) 화면에서

- 읽기(수집·자동 갱신)는 가린 화면에서도 된다. 학생은 체크히어 학생 번호(attendeeId)와 이 PC에 저장된 원문 기록으로 찾는다. 처음 보는 학생은 '연결 안 됨'으로 세고 건너뛴다.
- 쓰기(수정·삭제)는 **연결 프로그램 전용 크롬의 그 탭이 해제된 동안만**, 남은 해제 시간이 150초 이상일 때 시작한다(5절). 가린 동안 요청은 반려되지 않고 승인 대기(또는 승인됨) 그대로 남는다.
- 해제하는 법(사람이 한다):
  1. 수집 PC의 연결 프로그램 화면(`127.0.0.1:8765`)에서 「마스킹 해제 시작」 옆의 사유를 읽고 누르거나, 그 탭의 체크히어 머리말에서 직접 해제한다. 사유는 기다리는 실제 일이고, 그 글 그대로 체크히어에 들어간다.
  2. 메일로 받은 인증번호 6자리를 **그 화면에** 넣는다(연결 프로그램은 메일을 읽지 않는다).
  3. 해제되면 운영포털 「반영 요청·승인」에서 사람이 다시 반영한다(중계는 읽기 전용이라 쓰지 않는다). 연결 안 된 반은 연결 프로그램이 원문으로 다시 읽어 연결한다.
  4. 연장·종료는 **사람이 그 탭의 체크히어 머리말에서 직접** 누른다(연결 프로그램은 누르지 않는다). 새 탭은 다시 가려지므로 다른 탭에서 해제하면 소용없다.
- 도우미가 실패하면(`UNMASK_UI`) 그 탭에서 직접 「개인정보 마스킹 해제」를 누른다. 해제 창이 열린 동안 연결 프로그램은 화면을 옮기지 않는다(`MASKED_UNMASKING`).
- 해제로 풀리지 않는 것: 같은 반에 첫 글자·끝 4자리가 같은 학생(`MASKED_AMBIGUOUS`, 체크히어에서 직접 고침), 연결 충돌(`MASKED_CONFLICT`, 「연결 충돌 정리」 뒤 다시 수집), 저장 요청 확인 실패(`MASKED_GUARD`, 연결 프로그램 다시 시작).

## 3. 규칙 게시 (사용자)

`docs/checkhere-time-delete-rules.md`의 '게시 안내' 1~5번. 게시 전에는 삭제 요청 문서를 만들 수 없다(G3). Firestore 규칙은 이번에 바뀌지 않았다(`deleteTimes`·날짜 범위 2026-10-22 그대로, `settings/checkhereRelay`의 `privacy`는 관리자 쓰기 그대로).

## 4. 깃발 켜기와 첫 실제 삭제

체크히어에는 시험용 반·학생이 없다(Cowork 확인). 그래서 첫 삭제는 **실제로 지워야 하는 경우**(예: 결석인 학생에게 시간이 잘못 남은 경우)에 사용자가 지켜보며 한다. 삭제 요청은 /beta2의 ×와 결석 저장에서만 만들어지고, 이 화면은 깃발(G1)이 있어야 켜지므로 깃발을 먼저 켠다.

1. 데이터 탭에서 `settings/checkhereFeatures` 문서에 `timeDeleteRules`(boolean) `true`.
2. /beta2 출결대조에서 그 학생 행: 결석 저장(두 칸) 또는 퇴실 옆 ×가 켜졌는지 본다(꺼져 있으면 title에 이유). 확인창(지울 시간과 남는 것, 가려져 있거나 중계가 꺼져 해제 상태를 모르면 '반영할 때 체크히어 마스킹 해제 필요') → 3초 되돌리기 → 요청 1건(승인 대기).
3. 수집 PC 체크히어 탭의 마스킹을 사람이 해제한다(2-1절). 운영포털 「반영 요청·승인」 줄에 '체크히어 해제됨 · N분 남음 — 수정·삭제 가능'이 보이면 「요청 승인·반영」. 가려져 있으면 승인하지 않고 '체크히어 마스킹 해제가 필요합니다. …'를 보이며 요청은 그대로 둔다.
4. 확인할 것:
   - 체크히어 화면(새로고침): 1교시 `-`, 퇴실 `-`, 총 참여 시간 `-`. 입실은 남을 수 있다(사용자 결정: 괜찮음). 체크인 학생의 퇴실 삭제는 1교시(계산값)와 총 참여 시간도 `-`, 입실 시간은 그대로.
   - 요청 상태 '완료', 결과 글에 '퇴실·1교시 삭제 확인'(입실이 남으면 '입실 기록은 남음'). '일부 반영'이면 결과 글 '덜 지워짐: …'에 남은 종류·시간이 있다 — 체크히어에서 직접 확인하고 지운다. 체크인 학생의 퇴실 삭제 뒤 계산된 1교시가 남아도(측정과 다른 경우) '덜 지워짐: 1교시 …(PASS) 남음'이다.
   - `classes/{반}/checkhereCurrent/{날짜}`의 그 학생 `entry`(1교시)·`exit`가 비었음.
5. 이상하면 바로 6절로 끈다.

## 5. 마스킹 관문 (2026-10-16, 사용자 결정 "마스킹 해제를 요구하도록만")

- 기준(`rules.mjs` `privacyState`, 포털·연결 프로그램 공용): `masked` → '체크히어 가림 — 읽기만 가능 · 수정·삭제하려면 마스킹 해제 필요', `unmasked`이고 150초 이상 → '체크히어 해제됨 · N분 남음 — 수정·삭제 가능', 150초 미만 → '체크히어 해제 시간 N초 남음 — 연장해야 수정·삭제 가능', 모름 → '체크히어 해제 상태 확인 중'.
- 연결 프로그램: 쉬는 동안 15초마다 머리말만 읽고(이동·클릭 없음) `/api/status`·`/api/state`의 `privacy`로 알린다. 모든 수정·삭제(두 쓰기 방식, 바로 수정, 다시 처리, 승인 반영) 직전에 다시 읽어 쓸 수 없으면 체크히어를 건드리지 않고 해제 대기(MASKED_*)로 끝낸다. 머리말을 읽지 못한 상태(새로 띄운 뒤 아직 못 봄·모양이 바뀜)도 '확인 중'이라 쓰지 않는다. 여러 건이면 건 사이에 다시 보고 90초 밑이면 멈춘다. 해제 직후·쓰기 시도 뒤 1분은 연결 확인 수집(배우기)을 시작하지 않아 승인·반영을 누른 사람이 밀리지 않는다.
- 옛 연결 프로그램(가림 상태를 알리지 않음, 20261015.2 이전): 운영포털은 보내지 않고 '수집 PC에서 최신 체크히어 시작.cmd를 다시 실행해 주세요. … (privacy-state-v1) 지원이 필요합니다.'를 보인다(해제로는 풀리지 않음).
- 1기 운영포털 「반영 요청·승인」(지정 관리자): 화면이 보이는 동안 15초마다 `/api/status`를 읽어 안내 줄 끝에 해제 상태 글을 보인다. 승인·반영·일괄 승인·실패 건 다시 처리·바로 수정은 보내기 직전에 다시 보고, 쓸 수 없으면 보내지 않고 '체크히어 마스킹 해제가 필요합니다. 수집 PC의 체크히어 탭에서 해제(또는 연장)한 뒤 다시 반영해 주세요. 요청은 그대로 둡니다.'(남은 시간이 모자라면 해제 시간 글)를 보인다. 요청은 승인 대기(또는 승인됨) 그대로이고 실패·반려로 바꾸지 않는다. 수집·이미 반영 확인(읽기)은 막지 않는다.
- /beta2: 중계 신호의 `privacy`를 도구줄 중계 표시(짧은 글, title에 전체 글)에 보인다. 중계가 꺼져 있으면 해제 상태를 모른다('자동 수집·해제 표시 없음', title '체크히어 해제 상태는 중계가 켜져 있을 때 보입니다.'). 요청 만들기(×·결석 저장)는 가려도·중계가 꺼져도 되고(승인 대기), 가려져 있거나 해제 상태를 모르면 확인창과 × title에 '반영할 때 체크히어 마스킹 해제 필요'를 붙인다.
- 연결 프로그램 화면(`127.0.0.1:8765`): 마스킹 줄에 같은 해제 상태 글을 보이고 15초마다 다시 읽는다. 순차 수정 첫 1건이 확인을 기다리면 같은 줄에 알리고, 「확인했음」은 연결 프로그램의 `127.0.0.1:8765/writer` 화면에서 사람이 체크히어 값을 본 뒤 누른다.

## 6. 끄기와 되돌리기

- 끄기: `settings/checkhereFeatures.timeDeleteRules`를 `false`로 바꾸거나 문서를 지운다(G1). 중계를 멈춰도 삭제 요청 만들기는 꺼지지 않는다(2026-10-16). 반영은 늘 승인 때뿐이라 승인하지 않은 요청은 지워지지 않는다(대기로 남음). 관리자 1교시만 다시 막으려면 `rules.mjs` `ATTEND_DELETE=false`(웹·연결 프로그램 둘 다, build 올림).
- 잘못 지운 시간 되돌리기: 같은 칸에 시간을 다시 넣는다(/beta2 직접 요청이나 1기 요청으로 시간 요청). 체크히어는 빈 칸에 새 관리자 기록(새 기록 번호)으로 만든다(`existEventId:null`로 실제 확인). 지우고 다시 넣은 일은 변경 기록에 남는다.
- 실제 입실(ENTER)은 체크히어 화면에서 되돌릴 방법이 없다. 그래서 어떤 경로로도 지우지 않는다.

## 7. 참고

- 삭제 요청은 1기 '실패 건 다시 처리'와 일괄 승인에서 빠진다(개별 승인만, `checkhere-live-core.mjs` `retryInLedger`).
- 직접 수정(연결 프로그램 화면의 바로 수정)은 삭제를 받지 않는다.
- 연결 프로그램이 `time-delete-v1`을 모르면(옛 build) `/api/apply` 전에 거절한다. `time-delete-v2`를 모르면 1기 운영포털이 1교시가 들어간 삭제 요청의 승인을 거절한다('1교시 삭제는 time-delete-v2 지원이 필요합니다').
- 중계는 읽기 전용이다(2026-10-16). 요청을 승인·반영·반려하지 않고, 해제를 알아채도 쓰지 않는다.
