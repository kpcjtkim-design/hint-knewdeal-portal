# 체크히어 실시간 수정 (베타) — 2026-10-12

주소: `/checkhere-live.html` (메뉴에 넣지 않은 별도 페이지). 기존 포털 화면과 Firestore 규칙은 바꾸지 않았다.

## 흐름

1. **관리자 전원**(users.role=ADMIN 또는 기본 관리자)이 반·날짜 표를 실시간으로 본다. 화면은 `classes/{반}/checkhereCurrent/{날짜}` 문서 1개와 그 반·날짜의 `checkhereRequests`만 구독한다.
2. 수정하면 기존 `checkhereRequests` 형식 그대로 `pending` 요청이 만들어진다. 근거 앞에 `[실시간 베타]`, 끝에 `[기준:xxxxxxxx]`(수정 창에서 본 값의 지문)가 붙는다.
3. 수집 PC에서 **hint.kpc 계정으로 연 베타 탭의 '수집 PC 중계'**가 이 표시가 있는 관리자 요청만 골라 처리한다.
   - 현재 체크히어 값을 다시 읽는다(`/api/preview-request`). 지문이 다르면 반영하지 않고 반려 사유를 남긴다.
   - 기존 승인 규칙(`requested:true`)으로 점검 → 승인 → `/api/apply`. 연결 프로그램이 입력하고, 다시 열어 확인한 뒤 요청 결과와 `checkhereCurrent`를 저장한다(기존 검증 경로 그대로).
   - 표시가 없는 요청, 담임 계정 요청은 건드리지 않는다. 같은 요청이 스스로 5번 실패하면 반려한다. 연결 프로그램이 꺼져 있거나 로그인이 풀린 경우는 계속 기다린다.
4. 평일 08:50~18:40에는 5분마다 오늘 날짜 1~17반을 `mode:'incremental'`로 갱신한다. 화면에 보이는 행(실제 입실·교시·퇴실·외출)이 마지막 완전 수집과 같으면 수정창을 열지 않고, 바뀐 학생만 상세를 읽어 DB에 저장한다. 오늘 강의가 없는 반은 그날 자동 갱신에서 빠진다('이 반 지금 갱신'은 다시 시도).
5. 작성자는 처리 전(`pending`) 요청을 취소할 수 있다(기존 withdraw 규칙).

## 연결 프로그램 변경 (build 20261012.1)

- `collector.collect(..., {unchanged})`, 행 지문 `tableSignature`(참여시간 총계 제외), `sameTableRow`.
- `/api/sync`의 `mode:'incremental'`: 변경 없는 학생은 SQLite 기록도 추가하지 않는다. 일반 수집은 그대로.
- 능력 `incremental-sync-v1`. `Start.ps1`의 빌드 확인값도 갱신(실행 중인 옛 버전을 자동 재시작).

## 제한

- 실제 반영은 수집 PC가 한다. 그 PC가 켜져 있고, 체크히어에 로그인돼 있고, 중계 탭이 열려 있어야 한다. 중계 창은 최소화하지 않는 것을 권장한다(타이머는 워커로 돌려 백그라운드 지연을 줄였다).
- 첫 갱신은 학생별 수정창을 모두 열어야 해서 오래 걸린다. 진단(`체크히어 데이터진단.cmd`) 결과 메모·외출이 화면 데이터에 들어 있으면 이 부분을 빠른 방식으로 바꿀 수 있다.
- Firestore 규칙의 날짜 범위가 `2026-10-22`까지다. 2기에서 쓰려면 규칙과 `cleanRequest`의 날짜 범위를 함께 넓혀야 한다.
- 브라우저가 '로컬 네트워크 접근'을 물으면 허용해야 중계가 연결 프로그램에 닿는다.

## 사용량 (보장값 아님)

- 화면 1개: 문서 1개 구독, 변경될 때마다 읽기 1건. 수정 요청 구독은 그 반·날짜 요청만.
- 자동 갱신: 바뀐 반만 저장(서버 확인 읽기 약 3건 + 쓰기 1건). 바뀐 게 없으면 Firestore 접근 없음.
- 수정 1건: 요청 생성 1, 승인 1, 결과·현재 문서 저장 1~2 쓰기 + 확인 읽기.
