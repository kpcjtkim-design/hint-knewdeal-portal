# HINT 체크히어 검수 v0.2 · 지정 관리자 수정

반·날짜별 실제 입퇴실, 입실·교시 및 퇴실 관리자 메모, 외출 구간을 읽어 검토하고, 수정 근거와 변경 전후를 확인한 뒤 체크히어에 반영하는 Windows·macOS 로컬 연결 프로그램입니다. AI API를 호출하지 않습니다.

## Windows에서 실행

1. `체크히어 시작.cmd`를 더블클릭합니다. 크롬에서 `http://127.0.0.1:8765`가 열립니다.
2. **체크히어 로그인**을 누르고 새 전용 크롬 창에서 로그인합니다. 기존 크롬 로그인 정보를 복사하지 않습니다.
3. 반과 날짜를 선택하고 **체크히어에서 수집**을 누릅니다. 기간은 최대 31일이며 현재 UI는 평일 강의를 대상으로 합니다.
4. 수정은 **운영 포털 → 체크히어 → 검토·수정**에서 지정 계정으로 로그인하여 처리합니다. 다른 관리자는 수집·조회만 가능합니다. 독립 실행 화면에서는 직접 수정하지 않습니다. 시간 공란으로 지우기와 삭제는 지원하지 않습니다.
5. 결과가 `검증 완료`인지 확인합니다. `일부 실패`, `충돌`, `결과 미확인`이면 재수집 후 실제 값을 확인합니다. 불확실한 저장을 자동 재시도하지 않습니다.

이 개발 PC에서는 Codex에 포함된 Node와 Playwright를 자동으로 찾습니다. 배포용 Windows 묶음은 Node와 Playwright를 함께 포함하고, PC에 Chrome이 설치되어 있어야 합니다. 다른 PC에서 소스만 실행하려면 Node 24 이상과 이 폴더의 `npm install`이 필요합니다.

## macOS에서 실행

1. Google Chrome과 Node.js 24 이상을 준비합니다. `체크히어 시작.command`는 프로젝트의 `runtime/node`, Codex 런타임, Homebrew, Volta, asdf, mise 및 일반 PATH 순서로 Node를 찾습니다.
2. `체크히어 시작.command`를 더블클릭합니다. Git clone으로 받은 파일은 실행 권한이 유지됩니다. ZIP 등으로 받아 실행 권한이 사라진 경우 터미널에서 `chmod +x "체크히어 시작.command"`를 한 번 실행합니다.
3. 첫 실행에서 Playwright가 없으면 같은 폴더의 `package.json`을 기준으로 npm 의존성을 자동 설치합니다. Playwright 자체 Chromium은 받지 않고 설치된 Google Chrome을 사용합니다.
4. `http://127.0.0.1:8765`가 Chrome에서 자동으로 열립니다. **체크히어 로그인**을 누르고 새 전용 Chrome 창에서 로그인합니다. macOS에서도 `data/chrome-profile`에 전용 로그인 세션이 유지됩니다.
5. 운영 포털의 **체크히어** 탭에서 로컬 화면의 연결 키를 입력하고 수집합니다. 브라우저가 로컬 네트워크 접근을 묻는 경우 허용해야 합니다.
6. 이후 수집·검토·지정 관리자 수정·Firebase 보관 흐름은 Windows와 동일합니다. Windows의 `Start.ps1` 및 `.cmd` 파일은 그대로 유지됩니다.

> macOS 실행기는 Apple Silicon과 Intel Mac의 일반적인 Homebrew 경로를 모두 확인합니다. 실제 체크히어 화면 DOM과 로그인 정책은 Windows와 동일한 Playwright 수집기를 사용하므로, 최초 배포 후 실제 Mac에서 로그인 → 1개 반·1개 날짜 수집 → 읽기 전용 검수까지 먼저 확인한 뒤 수정 기능을 사용하는 것을 권장합니다.

## 플랫폼 연결

관리자 **체크히어** 탭에서 넓은 검수 화면을 바로 엽니다. 윈도우 연결 프로그램 설정에 이 PC 화면의 연결 키를 입력합니다. 브라우저에서 로컬 네트워크 접근을 묻는 경우 해당 연결을 허용해야 합니다. 키는 플랫폼 화면 메모리에만 보관하며 서버를 재시작하면 바뀝니다.

플랫폼에서 수집하면 결과를 `classes/{반}/checkhereSnapshots/{작업ID_날짜}`에 자동 보관합니다. 별도 ‘플랫폼에 저장’ 버튼으로 다시 저장할 수 있습니다. 플랫폼 보관에 실패해도 로컬 수집 성공과 구분해 안내합니다. 연결 프로그램 없이도 플랫폼의 과거 저장본은 조회할 수 있습니다.

현재 독립 실행 화면은 PC에만 저장합니다. 서버 자동 보관은 플랫폼 화면을 열고 연결한 상태에서 동작하며, 화면을 닫은 뒤에도 실행되는 예약 수집·백그라운드 업로드는 아직 구현하지 않았습니다. 다른 PC의 관리자는 플랫폼 보관본을 조회할 수 있습니다.

## 현재 수정 흐름과 보존된 요청 기능

- 현재 요청·승인 목록과 담임 요청 화면은 숨김 상태입니다. 구현과 기존 기록은 보존하며 `index.html`의 `CHECKHERE_REQUESTS_VISIBLE`로 노출을 제어합니다.
- **hint.kpc@gmail.com의 인증된 Google 로그인**만 학생별 ‘검토·수정’을 사용할 수 있습니다. 다른 관리자는 수집·조회·플랫폼 보관 및 내려받기만 가능합니다.
- 지정 계정은 수정 근거와 변경 전후를 확인한 뒤 ‘체크히어에 반영’을 누릅니다. 별도 승인 목록을 거치지 않습니다.
- 내부에서는 기존 `checkhereRequests`의 변경 전후 기록과 승인 검증을 재사용합니다. 서버는 지정 계정의 ID 토큰과 승인 문서를 검증하므로 버튼만 우회해도 다른 계정은 수정할 수 없습니다.
- 수정 전 원본 버전 확인, 중복 반영 방지, 저장 후 재조회 검증은 유지합니다. 응답이 끊기면 같은 창의 동일 변경은 기존 처리 상태를 확인하며 새 쓰기를 반복하지 않습니다.
- 결과 미확인·부분 실패는 재수집해서 확인합니다. 요청 목록을 다시 노출하면 기존 ‘반영 결과 확인’도 사용할 수 있습니다.
- 연결 프로그램 build `20260910.5` 이상이 필요합니다. 이번 화면 개편은 서버 프로토콜을 유지하므로 이미 해당 버전을 실행 중이면 재시작할 필요가 없습니다.

**플랫폼 배포에는 웹 파일과 변경된 `firestore.rules`를 함께 검토·적용해야 합니다.** 기존 운영 데이터나 권한 규칙은 이 프로그램 실행만으로 변경되지 않습니다. 새 보관 경로는 기존 관리자만 읽고 생성할 수 있으며 수정·삭제는 거부합니다. 배포 전 실제 관리자 인증 및 저장 권한 확인이 필요합니다.

## 판단 범위

- Workpack 1.2.1과 제공된 출결 규정의 09:00–18:00, 점심 12:00–13:00, 입실 10분·퇴실 10분 유예를 적용합니다.
- 09:10의 초 단위 경계는 매뉴얼에 명확한 기준이 없어 확인 대상으로 남깁니다.
- 실제 참여시간은 강의시간 밖과 점심, 겹치는 외출 구간을 제외해 계산합니다. 화면의 실제 참여시간은 최종 인정 교육시간과 구분합니다. 50% 근처의 유예·인정 시간 적용은 검토가 필요합니다.
- 인정출석은 시간만으로 확정하지 않습니다. 인지한 과거 시트 값은 ‘과거 시트’로 표시합니다. 현재 버전은 실시간 Google Sheet·수기·인정서류 수집을 추가하지 않습니다.
- 중복 출결, 사용자 정상 확인 후 반영 제외된 기록, 다른 강의시간, 입실과 교시 시간이 다른 기록은 자동 반영하지 않습니다.
- 실제 입실과 교시 기록을 각각 보관합니다. 오늘 수업이 끝나기 전 퇴실·교시 기록이 비어 있는 경우는 ‘진행중’으로 구분합니다. 지난 날짜의 두 시간이 다르면 수집 실패가 아니라 기록 불일치로 표시하고 반영을 제한합니다.
- 확인된 결석의 공란을 정상으로 유지하며, 출결 시간 공란만으로 무단결석이라 확정하지 않습니다.
- 현재 실제 사이트에서 확인한 단일 교시 표에 대응합니다. 다중 교시·화면 구조 변경 시 실패로 표시합니다. 17개 반 메뉴와 페이지 탐색을 구현했으며, 모든 반의 실제 구조 검증은 별도 수행해야 합니다.

## 체크히어 API 진단 (읽기 전용)

체크히어가 이름·전화번호·메모를 가려 보여 주면서(2026-10-15) 가린 상태에서 학생을 무엇으로 찾을지 정하려고 만든 진단입니다.
실제 체크히어에서 처음 돌리기 전에 사용자 확인을 받습니다.

1. 전용 크롬이 체크히어에 로그인된 상태에서 `체크히어 API진단.cmd`를 더블클릭합니다. 연결 프로그램이 꺼져 있으면 먼저 띄웁니다.
   - build `20261015.2`부터 있습니다. 쉬고 있는 옛 연결 프로그램은 다시 띄우므로 **연결 키가 바뀝니다**(중계 탭·운영포털에 새 키). 수집·반영 중이면 띄우지 않고 멈춥니다.
2. 반 번호와 두 날짜를 넣습니다. Enter만 누르면 오늘과 직전 교육일(평일, 강의 없는 날은 하루씩 앞으로)입니다.
3. 두 날의 출결상세 화면을 수집 때처럼 열고, **화면이 스스로 받은 출결상세 응답**만 셉니다. 체크히어에 따로 요청을 보내지 않습니다(토큰을 읽지 않고 체크히어 주소를 직접 부르지 않음). 변경·삭제·정상처리는 누르지 않고 수집 기록도 바꾸지 않습니다. 마스킹 해제(메일 인증번호)는 하지 않습니다.
4. 결과는 `data/probe/api-probe-{반}-{날짜}_{날짜}-*.json`에 저장되고 요약이 창에 나옵니다. 적는 것: 응답 모양(키 경로·형식·개수, 값으로 만든 키는 `{key}`), 이름·전화번호·메모의 가림/원문 개수, attendeeId 유무·빠진 학생 수·하루 안 중복·두 날짜에 같은 번호인지(번호끼리만 비교), 응답 날짜가 연 날짜와 같은지(예/아니오), 기록 종류별 기록 번호·관리자 메모 개수, 학생 명단 표의 전화번호 가림/원문 칸 수, 화면이 부른 체크히어 요청의 틀 이름·상태. 이름·전화번호·메모 내용·시간·id 값·토큰은 적지 않습니다.
5. 해제 상태와 비교하려면 사용자가 직접 해제한 10분 안에 한 번 더 실행합니다. 해제가 화면 이동 뒤에도 유지되는지는 아직 확인되지 않았으니, 요약의 날짜별 '화면' 줄(명단 전화번호 가림/원문 칸 수)로 실제 상태를 봅니다.
6. attendeeId가 두 날짜에 같다고 나와도 가림 상태로 바꿀 수 있는 것은 **수집(읽기)뿐**입니다. 수정·삭제는 체크히어가 해제를 요구하고, attendeeId와 포털 학생(이름·전화번호) 연결은 학생마다 한 번 원문 확인이 필요합니다.

포털이나 다른 도구에서는 `POST /api/api-probe`(`x-hint-key` 필요, 본문 `{classId, date1?, date2?, url?}`)를 부르고 `/api/state`의 작업(`kind: api-probe`) 진행을 봅니다. 능력 이름은 `api-probe-v1`입니다.

## 체크히어 개인정보 가림 화면 (build `20261015.3`, `masked-identity-v1`)

- 가린 화면에서도 수집합니다. 학생은 체크히어 학생 번호(attendeeId)를 이 PC SQLite의 연결(`attendee_links`)로 이어 찾고, 이름·학생 키는 저장된 원문 기록에서 씁니다. 가린 글자(`*`)는 이름·키·메모로 저장하지 않습니다.
- 수정·삭제는 이 연결 프로그램 전용 크롬의 그 탭이 해제된 동안만 합니다. 해제는 이 화면의 「마스킹 해제 시작」(사유 미리 보기 → 메일 인증번호는 사람이 넣음)이나 그 탭에서 직접 합니다. 연장·종료는 사람이 누릅니다.
- 운영 순서와 오류 글(`MASKED_*`)의 뜻은 `docs/checkhere-time-delete-enable.md` 2-1절에 있습니다.

## 수집·수정 방향 변경 (build `20261016.1`, `event-request-v1`)

- **학생 맞춤**: 표 순번(=화면 데이터 sequence)으로 먼저 맞추고 체크히어 학생 번호(attendeeId)를 1차 키로 씁니다. 기록에도 `attendeeId`를 붙이지만 학생 키·기록 id·버전 공식은 그대로이고 버전에는 넣지 않습니다(옛 저장본과 비교 그대로, 옮겨 쓰기 없음). 학생 번호는 이 PC SQLite에만 두고 응답·플랫폼 저장에서는 뺍니다.
- 전화가 다 보이지 않는 줄이 있어도 그날을 멈추지 않습니다(예전 「전화번호 표시가 필요합니다」). 이미 연결된 학생은 학생 번호로 찾고, 연결이 없는 학생만 '연결 안 됨'으로 셉니다. 연결표는 과정이 끝날 때까지 지우지 않습니다(21일 삭제 끔).
- **빠른 수집**(`incremental`): 그날 화면 데이터만 읽고 수정창을 열지 않습니다(표본 대조·수정창 대체 읽기 끔). 표와 맞지 않는 학생은 저장본을 그대로 두고 '확인 필요'로 셉니다. 화면 데이터를 못 받으면 `PAGE_NODATA`로 그날을 멈춥니다. **정밀 수집**(`full`)은 비상용으로 남고, 가린 화면에서는 시작하지 않습니다(`MASKED_PRECISE`).
- **이동**: 반 첫 스캔에서 강의 화면이 받은 일정 목록으로 날짜별 출결상세 주소를 한 번에 배워 `places`에 둡니다. 그 뒤 날마다 주소 이동 한 번, '보기' 누르기 없음, '실제 시간 기반' 두 번째 응답은 기다리지 않음, 날 사이 1~2초 쉼.
- **쓰기 재확인**: 다시 읽을 때 화면 데이터로 먼저 보고, 표와 맞지 않는 그 학생만 수정창으로 읽습니다. 가린 화면에서 다시 읽지 못한 결과는 `unknown`입니다.
- **형식 기록**(이 PC 화면에서만): `POST /api/record-format/start`(멈춤 `/stop`). 해제된 그 탭에서 사람이 수정창으로 한 건을 고치는 동안, 나가는 변경·삭제 요청 하나의 방식·주소·본문 구조(키·값 종류·typeEvent)만 `data/format/event-request-format.json`에 적습니다. 값·헤더·토큰은 적지 않습니다. 기록 중에는 정해진 저장 확인창만 받습니다.
- **순차 수정**: `/api/apply`·`/api/apply-batch`에 `writer:'request'`. (build `20261016.2`부터 켜기·형식 기록 단계 없음, 아래 절) 머리말 '원문 표시 중'·남은 150초 이상이어야 합니다. 요청은 로그인·해제된 체크히어 화면 안에서 그 화면이 붙이는 헤더로 보냅니다(연결 프로그램은 토큰·헤더 값을 받지 않음). 한 건씩 보내고 → 다시 읽어 대조 → 0.5~1초 쉬고 다음, 오류·불일치·해제 끝남에서 멈춥니다. 첫 실행은 build마다 1건이고, 그 건이 확인·저장된 뒤 `POST /api/request-writer/confirm`(「확인했음」)으로 풉니다. `preview:true`는 보내지 않고 바꿀 칸만 돌려줍니다.

## 두 칸 삭제·가림 확인 (build `20261016.2`, `time-delete-v2`·`privacy-state-v1`)

2026-10-16 실제 체크히어에서 확인한 동작(`docs/cowork/2026-10-16-checkhere-write-format.md` 2-1~2-3)에 맞췄습니다.

- **두 칸 삭제**(`writeback.applyVerified`, 수정창·순차 요청 같은 순서): 퇴실 먼저 지우고 → 다시 읽고 → 1교시가 아직 번호 있는 관리자 기록(ATTEND)이면 **다시 읽은 기록 번호로** 지우고 → 다시 읽어 퇴실·1교시가 모두 빈 것을 확인합니다. 결과 글은 `퇴실·1교시 삭제 확인`(입실 기록이 남으면 `· 입실 기록은 남음` — 사용자 결정: 남아도 됨). 덜 지워지면 `partial`, 글은 `덜 지워짐: 1교시 18:00:00(ATTEND) 남음 …`(종류·시간만).
- 퇴실이 남은 채 1교시만 지우는 요청은 누르기 전에 거절합니다(체크히어가 퇴실 시간으로 입실·1교시를 다시 채움). 퇴실만 지우기는 그대로이고, 1교시만은 퇴실이 이미 빈 뒤에만 됩니다. 체크인한 학생의 계산된 1교시(PASS)는 퇴실과 함께 비고, 지울 칸이 아닙니다. 규칙은 `rules.mjs` `timeDeleteRefusal`(`ATTEND_DELETE=true`, `DELETE_ORDER=['exit','entry']`)로 포털과 같습니다.
- **가림 확인(쓰기 관문)**: 수정·삭제는 사람이 그 탭을 해제했고 남은 시간이 150초 이상일 때만 잡고(`PRIVACY_MIN_WRITE_SECONDS`), 칸마다 쓰기 직전에 머리말을 다시 읽어 90초 밑이면 멈춥니다. 막히면 아무것도 누르지 않고 `MASKED_WRITE`(`NEEDS_UNMASK_TEXT`)·`MASKED_TIME`으로 요청을 승인 상태 그대로 둡니다. 가림 기능을 본 탭에서 머리말을 읽지 못하면 쓰지 않습니다. 해제·연장·종료는 연결 프로그램이 누르지 않습니다. 읽기(빠른 수집)는 가려져도 됩니다.
- **가림 상태 알림**: `GET /api/status`(가벼움: build·능력·바쁨·`privacy`)와 `/api/state`의 `privacy` = `{state:'masked'|'unmasked'|'unknown', leftSec, writable, text}`(이름 없음). 쉬는 동안 15초마다 머리말 글만 읽습니다(이동·클릭 없음).
- **순차 수정**: 내장 형식(2026-10-16 기록의 방식·주소·본문 키)으로 기록 없이도 씁니다(새로 기록한 형식이 있으면 그 종류가 우선). 켜기(`/api/request-writer/arm`)는 없어졌고 불러도 상태만 돌려줍니다 — 사람의 마스킹 해제가 관문입니다. 체크히어 탭 안 장치(`event-request.mjs privacyHook`)가 화면이 스스로 보내는 관리자 API 요청의 인증·해제 헤더를 그 탭 안에만 두고, 순차 요청도 그 탭 안에서 같은 헤더로 보냅니다. 우리 코드는 헤더 값을 돌려받거나 읽거나 저장·기록하지 않습니다(화면 장치가 돌려주는 것은 있음/없음·상태·code뿐). 다만 Playwright가 화면의 요청·응답 사건(수집기의 응답 감시, 쓰기 확인의 `page.route`)을 넘기며 요청 머리(헤더 값 포함)가 연결 프로그램 프로세스 메모리를 잠시 지납니다 — 우리 코드는 그 헤더를 보지 않습니다. 해제 헤더를 아직 못 봤으면 「실제 시간 기반」↔「강의 출석/퇴실 허용 시간 기반」 라디오를 한 번 바꿨다 되돌려 화면이 다시 읽게 합니다.
- 쓰기 방식을 정하지 않은 반영(포털·직접 수정)은 순차 요청이 준비되면 그것, 아니면 수정창입니다. build마다 첫 1건만 순차 요청으로 합니다. 쓰기 단계까지 간 첫 건은 결과와 상관없이 그 차례를 쓰고, 그 뒤에는 사람이 `http://127.0.0.1:8765/writer`에서 「확인했음」을 누를 때까지 나머지는 수정창으로 반영합니다(막지 않음). 첫 건이 확인·플랫폼 저장까지 끝났으면 「확인했음」이 순차 수정을 켜고, 끝까지 확인되지 않았으면(실패·덜 지워짐·충돌·미확인) 체크히어 원본을 본 뒤 누른 「확인했음」은 다음 1건만 다시 순차 요청으로 해 봅니다(같은 잘못이 건마다 되풀이되지 않게). 순차 요청으로 실패한 같은 건을 수정창으로 저절로 다시 쓰지 않습니다.

## 기록 보존과 검증

`data/attendance.sqlite`에 수집 원본을 추가 저장하고, 수정 전후 및 저장 확인 과정을 기록합니다. `data/chrome-profile`에는 이 전용 크롬의 로그인 세션이 남습니다. 두 폴더 모두 Git 및 배포 묶음에서 제외합니다. 출결 원본이나 사용자 파일을 삭제하는 기능은 없습니다. 수집 실패를 빈 메모로 바꾸지 않습니다.

쓰기 직전 이름과 식별정보, 시간·메모·외출 구간을 다시 대조합니다. 입실·퇴실 저장은 각각 별개 작업이므로 부분 성공이 가능합니다. 각 저장 후 화면을 다시 열고 값을 읽어야만 검증 완료가 됩니다. 다른 관리자의 변경이 발견되면 중단합니다. 동일한 요청 식별자는 한 번만 처리합니다.

```text
node server.mjs

```

시간 경계, 점심·외출 중복, 인정출석 구분, 메모 누락·불일치, 동일 이름 식별, 저장 직전 충돌, 부분 성공, 응답 끊김 후 재조회, 중복 요청, 로컬 API 접근 제한과 실제 DOM 형태의 가상 수정 창을 시험합니다. 테스트는 가상 학생을 사용하며 체크히어 운영 출결을 바꾸지 않습니다.

기존 실제 날짜·반 수집과 사유 수정은 사용자가 확인했습니다. 승인 기능은 가상 학생으로 요청 작성, 지정 관리자 제한, 변경 전후 표시, 저장 실패, 요청 위변조·중복 실행 방지와 토큰 검증을 시험합니다. 실제 학생의 출결을 변경하는 시험은 수행하지 않습니다. 운영 배포 및 실제 로그인 검증 결과는 별도 보고합니다.
